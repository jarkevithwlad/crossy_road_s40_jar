# План переноса Expo Crossy Road на Nokia Series 40 (Java ME, настоящее 3D)

## Статус документа

- Это только план. Реализация игры ещё не начата.
- Рабочая папка будущего порта: `nokia-s40-port/`.
- Исходный Expo-проект остаётся неизменным и используется как эталон поведения и внешнего вида.
- Для сборки используются JDK 8 и поставляемые вместе с портом Java ME API stubs, M3G stubs и ProGuard; исходный Expo-проект нужен только для необязательной регенерации ассетов.
- Другие соседние проекты не входят в область работ и больше не исследуются.
- Начало этапа 1 возможно только после одобрения этого плана.

## 1. Итоговая оценка выполнимости

Переписать игру на нативной Java ME с настоящей трёхмерной сценой возможно. Прямо перенести React Native, Three.js, GSAP, OBJ-загрузчик и исходные модели нельзя: их нагрузка слишком велика для Series 40. Но можно сохранить объёмное ощущение оригинала с помощью полноценной 3D-геометрии, ортографической камеры, глубины, вращения моделей, освещённых граней и трёхмерного движения.

Основной рекомендуемый рендерер — Mobile 3D Graphics API (M3G, JSR-184) в immediate mode, если целевой телефон поддерживает JSR-184. M3G специально предназначен для 3D на CLDC/MIDP-устройствах. До разработки всей игры это обязательно проверяется небольшим Device Probe и нагрузочной сценой.

Если конкретный телефон не поддерживает M3G либо его реализация окажется нестабильной, запасной путь — собственный software 3D renderer на Java ME: fixed-point преобразования, back-face culling, painter sorting и плоская заливка треугольников через LCDUI. Это также останется настоящим 3D, но потребует более строгого ограничения геометрии и даст меньший FPS.

### Предварительный вердикт по производительности

Производительности должно хватить при следующих условиях:

- в обычном кадре отправляется примерно 600–900 видимых треугольников;
- тяжёлый кадр с поездом ограничен примерно 1 200–1 500 треугольниками;
- дальние ряды и объекты используют упрощённый LOD;
- в телефоне не загружаются и не разбираются OBJ-файлы;
- координаты, индексы и данные моделей заранее квантуются и упаковываются;
- отсутствуют динамические shadow maps, per-pixel lighting и прозрачная сортировка большого количества объектов;
- игровой цикл не создаёт новые объекты и массивы в каждом кадре;
- логика работает с фиксированным шагом независимо от FPS рендера.

Инженерная цель — 20 FPS в обычной игре, допустимый минимум — стабильные 15 FPS, желаемый результат на более быстром S40 — 25–30 FPS. Это пока бюджет, а не обещание для неизвестной модели телефона. Окончательный вывод будет сделан после теста 300/600/900/1200/1500 треугольников на реальном устройстве.

## 2. Что изучено в текущей игре

### 2.1 Технологии оригинала

- Expo 54, React Native 0.81 и Expo Router.
- Three.js 0.182 через `expo-gl` и `expo-three`.
- Ортографическая камера и фиксированный наклон, создающие фирменный изометрический вид.
- GSAP/Tween для прыжков, поворотов, деформации героя, воды и UI.
- OBJ-модели с PNG-текстурами, Lambert material, направленный и окружающий свет.
- Тени, частицы воды/перьев/пены/дыма и звуки.
- Портретная ориентация.

### 2.2 Фактическая игровая механика

- Игрок перемещается прыжками ровно на одну клетку вперёд, назад, влево или вправо.
- Обычный прыжок длится примерно 0,2 секунды и включает подъём, приземление, сжатие и поворот модели.
- Счёт — максимальное число рядов, пройденных вперёд от стартовой позиции.
- Камера плавно следует за продвижением и немного смещается по горизонтали.
- Смерть наступает от машины, поезда, воды, ухода за боковые границы либо отставания за нижнюю границу камеры.
- На брёвнах игрок движется вместе с объектом.
- На кувшинках используется статическая опора и анимация проседания.
- Деревья и валуны блокируют переход в клетку.
- Карта бесконечно достраивается впереди и переиспользует пулы рядов.

### 2.3 Генерация рядов, которую нужно сохранить

- В начале создаётся безопасная травяная зона вокруг стартовой позиции.
- После неё базовый выбор равновероятен между травой, дорогой/железной дорогой и водой.
- Внутри дорожной категории примерно четверть рядов становится железной дорогой, остальные — автомобильной дорогой.
- На дороге движутся 1–2 машины с единым направлением и скоростью для ряда.
- На воде размещаются 2–3 объекта: чётные ряды используют кувшинки, нечётные — движущиеся брёвна.
- Трава имеет непроходимые боковые стены и случайные деревья/валуны в игровой области.
- Между травой и статической водой уже существует координация свободных клеток, уменьшающая вероятность непроходимой генерации.

### 2.4 Реально активный интерфейс

- Главный экран показывает логотип поверх живой 3D-сцены; нажатие начинает игру.
- Во время игры показываются текущий счёт и лучший результат.
- После смерти появляется game-over слой с кнопкой новой игры.
- В исходниках есть экраны персонажей, настроек, рекламы, share и leaderboard, но значительная часть кнопок закомментирована, недоступна или является заглушкой.
- Активен только персонаж Chicken; остальные модели персонажей исключены из реального выбора.

Порт повторяет работающую игру, а не переносит неработающие рекламные и сетевые заглушки. Настройки на S40 будут функциональными: звук, качество 3D, FPS/дальность и сброс рекорда.

### 2.5 Размеры и сложность исходных ресурсов

- Все ресурсы текущего проекта занимают около 3,7 МБ.
- Аудио занимает около 1,55 МБ.
- OBJ и их текстуры занимают около 1,26 МБ.
- Один Chicken содержит 210 треугольников.
- Одна машина содержит примерно 144–236 треугольников.
- Минимальный поезд из front/middle/back содержит 1 904 треугольника; дополнительные middle-секции увеличивают это число.
- Одна модель железной дороги содержит 530 треугольников.

Прямое использование этих сеток создаёт обычные кадры примерно на несколько тысяч треугольников и особенно тяжёлые кадры с поездом. Поэтому модели будут не превращены в плоские картинки, а вручную/автоматически упрощены до low-poly 3D-вариантов.

## 5. Архитектура настоящего 3D

### 5.1 Основной путь: M3G immediate mode

- `Graphics3D` привязывается к буферу `GameCanvas` только на время 3D-прохода.
- Камера использует параллельную/ортографическую проекцию и угол, визуально совпадающий с Three.js-оригиналом.
- Модели хранятся в компактных `VertexArray`, `VertexBuffer` и `TriangleStripArray`.
- Все повторяющиеся машины, деревья, валуны, брёвна и кувшинки разделяют одну геометрию; различается только transform.
- Геометрия группируется по материалу и LOD, чтобы уменьшить число render calls.
- Цвета граней и маленькие текстуры воспроизводят voxel-палитру оригинала.
- Один ambient и один directional light либо заранее запечённые цвета вершин заменяют дорогую систему света Three.js.
- Тени — простые полупрозрачные плоские квады под объектами, а не shadow maps.
- Прозрачные объекты рисуются отдельным коротким проходом после непрозрачных.

### 5.2 Запасной путь: software 3D

Он включается только если Device Probe покажет отсутствие или непригодность M3G.

- Fixed-point матрицы и преобразования координат.
- Ортографическая проекция без дорогого перспективного деления.
- Back-face culling до растеризации.
- Отсечение по видимым рядам и экранным границам.
- Painter ordering по объектам/группам и локальная сортировка граней.
- `Graphics.fillTriangle` для плоско закрашенных граней либо RGB565-буфер, если телефонный benchmark покажет, что он быстрее.
- Без полноэкранного z-buffer по умолчанию; его память и цена должны быть отдельно доказаны benchmark-тестом.

### 5.3 Почему это будет восприниматься как 3D

- Все игровые объекты имеют реальные X/Y/Z координаты и объёмную сетку.
- Камера видит верхние и боковые грани объектов.
- Герой физически поднимается по Y во время прыжка.
- Машины, брёвна и поезд движутся в мировом пространстве.
- Модели поворачиваются в четырёх направлениях, а не заменяются заранее нарисованной картинкой.
- Перекрытие объектов зависит от глубины сцены.
- Направленное освещение или vertex shading различает верхние, передние и боковые поверхности.
- Камера плавно движется по 3D-миру.
- Вода, перья и всплеск используют ограниченные 3D-квады/треугольники.

## 6. Бюджет треугольников

| Часть обычного кадра | Целевой бюджет |
|---|---:|
| Видимые поверхности рядов | 40–80 |
| Chicken, включая анимационные состояния | 80–120 |
| Деревья и валуны после culling/LOD | 180–300 |
| Машины, брёвна и кувшинки | 200–350 |
| Тени и небольшие эффекты | 20–60 |
| Запас на дополнительные видимые объекты | 80–150 |
| **Обычная сцена** | **600–900** |
| **Тяжёлая сцена с поездом** | **1 200–1 500 максимум** |

Ограничение относится к реально отправленным видимым треугольникам, а не ко всем объектам бесконечного мира. Закадровые ряды, боковые стены вне проекции и дальние мелкие объекты не отправляются в рендерер.

### Предлагаемые LOD сеток

- Chicken: 80–120 ближний LOD, 40–60 дальний.
- Легковая машина: 40–64 ближний, 20–32 дальний.
- Грузовик: 56–80 ближний, 28–40 дальний.
- Дерево: 16–28 ближний, 8–12 дальний.
- Валун: 12–24 ближний, 8–12 дальний.
- Бревно: 16–28 ближний, 8–12 дальний.
- Кувшинка: 8–12.
- Светофор железной дороги: 24–40.
- Секции поезда суммарно: ориентир 300–500 в тяжёлом кадре.

## 7. Offline-конвейер 3D-ресурсов

Телефон не должен читать текстовый OBJ. Будет создан desktop-only converter:

1. Прочитать активные OBJ и их палитровые PNG из текущего проекта.
2. Удалить невидимые внутренние и дублирующиеся грани.
3. Объединить копланарные поверхности там, где не меняется силуэт.
4. Подготовить ближний и дальний LOD.
5. Зафиксировать pivot, размер и ориентацию модели относительно оригинала.
6. Преобразовать координаты в signed short с scale/bias.
7. Упаковать индексы и группы материалов в компактный бинарный формат.
8. Свести текстуры к маленьким палитровым 16×16, 32×32 или 64×64 ресурсам только там, где текстура действительно нужна.
9. Для одноцветных voxel-граней использовать vertex colors/material colors без PNG.
10. Сгенерировать отчёт: вершины, треугольники, draw groups, compressed bytes и приблизительная decoded memory.
11. Добавить golden-превью каждого сконвертированного объекта рядом с исходным ракурсом.

Все сгенерированные runtime-файлы будут находиться внутри `nokia-s40-port/res/`. Исходные ассеты Expo не перемещаются и не изменяются.

Имена классов могут быть укрупнены после прототипа, если это заметно уменьшит JAR. Java-код остаётся совместимым с source 1.3: без generics, enum, lambdas, annotations и autoboxing.

### Правила памяти

- Примитивные массивы вместо коллекций в горячих участках.
- Ring buffer рядов вместо бесконечного накопления мира.
- Пулы машин, брёвен, частиц и временных transforms.
- Никаких `new`, конкатенации строк и загрузки ресурсов в игровом кадре.
- Одна копия геометрии для всех экземпляров одинаковой модели.
- Маленькая очередь ввода, которую callbacks только заполняют.
- Строки HUD обновляются только при изменении счёта/FPS/состояния.
- Пауза полностью останавливает обновление мира и звук.
- Memory ledger ведётся с первого прототипа; окончательный heap budget назначается после Device Probe.

## 9. Игровой цикл

- Один выделенный game thread, как в разрешённом образце.
- Logic timestep: фиксированный, ориентир 50 мс (20 Hz), с ограниченным догоняющим циклом.
- Render timestep независим от логики и ограничен выбранным quality profile.
- Движение машин, поезда, брёвен и камеры зависит от времени, а не от количества отрисованных кадров.
- Прыжок хранит нормализованный progress и интерполирует XYZ/rotation/scale.
- При очень низком FPS логика не должна ускоряться или замедляться.
- Ввод обрабатывается на game thread через ring queue.
- `startApp`, `pauseApp`, `hideNotify`, `showNotify` и `destroyApp` не создают второй одновременно работающий поток.

## 10. Управление на клавиатуре Nokia

| Действие | Основные клавиши | Резерв |
|---|---|---|
| Прыжок вперёд | джойстик вверх | `2` или `5` |
| Прыжок назад | джойстик вниз | `8` |
| Прыжок влево | джойстик влево | `4` |
| Прыжок вправо | джойстик вправо | `6` |
| Старт / повтор | центр джойстика | `5` |
| Пауза / меню | правая softkey | `7` как резерв |
| Быстрый restart после смерти | левая softkey | `*` как резерв |

Сначала используются абстрактные game actions `UP/DOWN/LEFT/RIGHT/FIRE`; конкретные numeric и softkey codes добавляются как совместимый fallback. Key repeat не должен создавать несколько неправильных прыжков, пока текущий прыжок ещё не принят логикой.

## 11. Камера и композиция кадра

- Ортографическая M3G camera (`setParallel`) вместо перспективной камеры.
- Угол и масштаб подбираются по эталонным скриншотам текущей игры.
- Chicken находится около нижней центральной трети экрана.
- Видно ориентировочно 10–14 рядов, но точное число определяется benchmark.
- Camera Z плавно догоняет прогресс игрока.
- Camera X мягко смещается, но остаётся ограничена, как в текущем `GameEngine`.
- Новый ряд создаётся только при пересечении следующей целой позиции камеры.
- Near/far clip и row culling исключают лишние объекты до render call.
- UI рисуется отдельным 2D-проходом после освобождения M3G target.

- четыре дерева, два валуна, четыре бревна и кувшинка либо их визуально близкие low-poly варианты;
- объёмная модель Chicken с четырьмя направлениями;
- плоские мягкие тени под объектами;
- сжатие/растяжение Chicken во время прыжка и смерти;
- небольшие перья и всплеск с жёстким лимитом частиц;
- логотип, счёт, TOP и экран смерти в стилистике оригинала.

### Что сознательно не переносится один в один

- shadow maps 2048×2048;
- antialiasing уровня Three.js;
- настоящий динамический Lambert light на каждый пиксель;
- большие текстуры 512–1024 px;
- неактивные персонажи и недоступный character picker на первой версии;
- рекламные баннеры, share, leaderboard и purchase-заглушки;
- React Native settings, не влияющие на игру.

## 13. Звук и сохранения

### Звук

- Использовать MMAPI только после Device Probe поддерживаемых content types.
- Выбрать небольшой набор: прыжок, машина/удар, смерть, вода, сигнал/поезд и UI.
- Сэмплы конвертировать в короткий mono low-rate формат, реально поддержанный телефоном.
- Не хранить одновременно несколько тяжёлых PCM-копий.
- Добавить `Sound: On/Off` и автоматически продолжать игру без ошибки, если аудиоплеер не создался.
- Исключить большой `car-engine-loop-deep.wav` и остальные неиспользуемые аудиофайлы.

### Сохранения

- RMS (`RecordStore`) хранит high score, звук, quality profile и выбранные параметры.
- Запись выполняется только при изменении настройки или завершении игры, не в кадре.
- Повреждённая/отсутствующая запись сбрасывается к безопасным defaults.
- Формат записи имеет version byte для будущей миграции.

## 14. Профили качества

После аппаратного benchmark будут оставлены только реально полезные параметры:

### Low

- 15 FPS cap;
- меньшая дальность рядов;
- дальний LOD включается раньше;
- меньше перьев/всплесков;
- простые vertex colors;
- минимальное число прозрачных теней.

### Normal

- 20 FPS cap;
- целевые 600–900 треугольников;
- полные near LOD в центре кадра;
- тени и основные частицы;
- маленькие текстуры и один directional light, если это быстрее запечённых вариантов на устройстве.

### High — только если доказан запас

- 25–30 FPS cap;
- немного больше видимых рядов;
- near LOD используется дальше;
- больше частиц.

Качество не переключает игру в 2D: все профили остаются настоящим 3D.

## 15. Сборка JAR/JAD

`build.ps1` будет основан на проверенной последовательности Minesweeper3D, но находиться и работать только внутри `nokia-s40-port`.

1. Проверить наличие разрешённого JDK 8, API stubs и ProGuard.
2. Очистить только собственные `nokia-s40-port/build` и нужные файлы собственного `dist`.
3. Скомпилировать compile-time stubs отдельно.
4. Скомпилировать production sources с `-source 1.3 -target 1.1`.
5. Скомпилировать и выполнить desktop unit tests.
6. Выполнить asset validation и render/device-profile tests.
7. Создать raw JAR только с production classes и runtime resources.
8. Запустить ProGuard `-microedition` для преверификации и StackMap.
9. Проверить class version 45.3, наличие StackMap и отсутствие stubs в JAR.
10. Проверить manifest и список ресурсов.
11. Создать JAD с вычисленным размером JAR.
12. Вывести размеры code/models/textures/audio и общий размер дистрибутива.

Планируемые файлы:

- `dist/CrossyRoadS40-M3G.jar`
- `dist/CrossyRoadS40-M3G.jad`
- software 3D вариант создаётся только при необходимости, доказанной Device Probe.

## 16. Тестовая стратегия

### 16.1 Unit tests на ПК

- движение по четырём направлениям;
- запрет движения в дерево/валун;
- очки только за новый максимальный ряд;
- посадка на кувшинку/бревно;
- перенос игрока движущимся бревном;
- столкновения с машиной и поездом;
- смерть в воде и за пределами сцены;
- генерация стартовой безопасной зоны;
- распределение типов рядов с фиксированным seed;
- отсутствие очевидно закрытого перехода grass → lily row;
- корректность ring buffer при длительном продвижении;
- fixed timestep при разных render FPS;
- очередь ввода и переполнение без повреждения состояния;
- сохранение/восстановление high score и настроек.

### 16.2 Asset tests

- каждый runtime mesh имеет допустимые индексы;
- нет нулевых/вырожденных треугольников;
- bounding box и pivot совпадают с manifest;
- LOD не превышает установленный triangle budget;
- texture dimensions поддерживаются выбранным профилем;
- ресурсы доступны по точному регистру пути внутри JAR;
- compile stubs не попали в JAR.

### 16.3 Render smoke tests

- стартовая сцена;
- трава с препятствиями;
- несколько дорожных рядов;
- вода с брёвнами и кувшинками;
- железная дорога с warning light;
- поезд в кадре;
- все четыре направления Chicken;
- прыжок, смерть от машины и падение в воду;
- home, HUD и game over;
- кадр сравнивается с golden image с допустимым порогом расхождения.

### 16.4 Performance tests

- отдельные сцены на 300, 600, 900, 1 200 и 1 500 треугольников;
- flat color против textured material;
- один большой draw group против нескольких маленьких;
- влияние света, blending, теней и HUD;
- время update, culling, render и flush измеряется отдельно;
- счётчики visible rows, objects, triangles, render calls и FPS выводятся debug overlay;
- измеряется heap до загрузки, после загрузки и после 10 минут игры;
- steady-state кадр не должен создавать мусор для GC.

### 16.5 Обязательные тесты на телефоне

- установка через JAD/JAR;
- холодный запуск и повторный запуск;
- pause/resume, вход системного меню и возврат;
- удержание/быстрые нажатия каждой клавиши;
- не менее 10 минут непрерывной игры;
- несколько появлений поезда;
- звук on/off;
- сохранение рекорда после закрытия MIDlet;
- отсутствие зависания, OOM, мерцания и пропущенного ввода;
- FPS в обычной и тяжёлой сцене.

## 18. Критерии готовности

Порт считается завершённым, когда одновременно выполнено следующее:

- JAR/JAD устанавливаются и запускаются на целевой Nokia.
- Сцена действительно 3D: M3G либо software polygonal renderer, без замены мира плоскими спрайтами.
- Обычная сцена укладывается в утверждённый triangle/FPS budget.
- Имеются grass, road, water и railroad rows.
- Работают Chicken, trees/boulders, все утверждённые машины, logs/lily pads и train.
- Работают все четыре прыжка, camera follow, score, high score, collision и death.
- Внешний вид каждого типа сцены принят по reference checklist.
- Нет зависимости скорости игры от FPS.
- Нет постоянных аллокаций/GC spikes в основном цикле.
- Игра выдерживает не менее 10 минут на устройстве без OOM и зависания.
- Pause/resume и системное скрытие/возврат не создают второй поток и не ломают звук.
- Рекорд и настройки сохраняются.
- Clean build создаёт повторяемый JAR/JAD и проходит автоматические тесты.
- В конечном JAR отсутствуют compile-time API stubs и desktop-only tools.

## 19. Основные риски и меры

| Риск | Мера |
|---|---|
| У телефона нет JSR-184 | Device Probe до основной разработки; software 3D как отдельный согласованный backend |
| M3G implementation медленный/ошибочный | Ранние реальные benchmarks, immediate mode, малые batches и quality profiles |
| Прямые модели слишком тяжёлые | Low-poly rebuild, LOD, triangle manifest и build gates |
| Недостаточный heap | Shared meshes, маленькие textures, primitive arrays, memory ledger, ограниченные pools |
| Большой JAR | Удаление OBJ/лишнего audio/UI, compact binary meshes, палитровые PNG, ProGuard |
| Мерцание при смешивании 3D и HUD | Строгий порядок bind/render/release, затем 2D HUD и один flush |
| Прозрачность/тени тормозят | Ограничить blending, упрощённые квады, возможность отключить тени в Low |
| Звук зависает или не поддерживается | Device Probe, короткие форматы, graceful mute fallback |
| Различаются key codes | Game actions плюс numeric/softkey fallback и input diagnostics |
| Бесконечная карта растит память | Ring buffer и фиксированные object pools |
| Порт переносит баги/заглушки Expo UI | Портировать фактически работающую механику; спорные отличия согласовывать отдельно |
| Права на оригинальные игровые ресурсы | Сохранить образовательное назначение и уведомления; отдельно проверить права перед распространением JAR |

## 20. Правила работы после одобрения

- Все новые production-файлы создаются только внутри `nokia-s40-port/`.
- Текущий Expo-проект используется только для чтения и сравнения.
- Разрешённый Minesweeper3D используется только как образец toolchain; его файлы не меняются.
- Другие локальные проекты не открываются и не используются.
- После каждого этапа выполняются build/tests, а результат кратко фиксируется в README или progress log.
- Сначала доказывается 3D/FPS/heap на маленьком прототипе, затем добавляется весь контент.
- Любое предложение заменить 3D на 2D требует отдельного явного согласования и не считается автоматическим fallback.
